# Story 27.3: Examples gallery hub (`/examples/`)

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a visitor comparing stacks,
I want a gallery of live wikis at `/examples/`,
so that I can pick the demo closest to my workflow and open a real generated wiki for it.

**INVEST:** I✓ N✓ V✓ E✓ S✓ T✓

**Demo path:** `npm run build && npm run build:examples -- --all && npm run build:site` → open `dist/landing-site/examples/index.html` → one card per catalog entry, each opening a live wiki under `examples/<slug>/html/index.html` with working CSS/search.

**Binds:** E27 S27.3 | **Depends:** S27.1 (manifest), S27.2 (`build:examples`) | **Blocks:** S27.6 (cross-example nav chrome)

**Trigger (pulled forward):** Owner requested the gallery now. Hero live proof (S27.1/S27.2/S27.4) is already in review; this story turns the single hero demo into the full multi-example gallery promised by the E27 v2 gate.

## Context

E27 shipped a **conversion-first** v1: one live hero wiki (`agent-harness-parcel`) linked from landing §04, generated by `scripts/build-examples.mjs --hero-only`. S27.3 is the deferred **breadth** slice: generate **all** catalog examples and add a browsable gallery hub page at the `/examples/` root so visitors can compare frameworks.

Honesty constraint from E27: never claim more live demos than actually exist. The manifest has **three** catalog entries today (`agent-harness-parcel`, `bmad-research-relay`, `article-research-mycelium`) — not five. All copy and card counts must derive from the manifest, not hardcoded numbers.

## Acceptance Criteria

### Functional

1. `npm run build:examples -- --all` generates a browsable wiki for **every** catalog entry in `examples/manifest.yaml` under `dist/landing-site/examples/<slug>/html/index.html` (already supported by S27.2 `--all`; this story exercises and verifies it end-to-end).
2. A gallery hub page is written to `dist/landing-site/examples/index.html`, rendered from `examples/manifest.yaml` as the single source of truth — one card per catalog entry showing `title`, `tagline`, and `framework`, each linking to that example's live wiki via a **relative** href `<slug>/html/index.html`.
3. The gallery page reuses the shared landing chrome — skip link, `[[specwiki]]` wordmark linking `../index.html`, primary `<nav>` with accessible name, `../assets/landing.css`, favicon/apple-touch-icon at `../assets/`, and a footer — mirroring the page shell in `scripts/build-blog.mjs`. All internal hrefs and asset `src`s are relative (subpath-safe); no `href="/…"` or `src="/…"`.
4. The hero example (`manifest.hero`) is visually distinguished on the gallery (e.g. ordered first and/or a "hero" badge) so the primary demo stays prominent.
5. Gallery generation is wired into the build so a normal deploy produces it: extend `scripts/build-examples.mjs` (or a small dedicated module it calls) to emit `examples/index.html` after generating the built slugs, and update `.github/workflows/deploy-site.yml` to run `npm run build:examples -- --all` (replacing `--hero-only`) with `npm run build` still preceding it.
6. Landing §04 secondary copy (`site/index.html`, the `.section-prose--secondary` paragraph) is updated to link to the **live gallery** (`examples/index.html`) instead of stating examples are "not yet hosted on specwiki.ai"; the count/wording is honest for the current manifest (three examples). The hero primary CTA and before/after panel in §04 are unchanged.

### Quality measures

7. Assert zero absolute-root `href="/` or `src="/` in the gallery `index.html` **and** across all generated example HTML trees (reuse `scripts/lib/assert-no-root-absolute-urls.mjs` → `assertNoRootAbsoluteUrlsInHtmlTree`).
8. Card titles, taglines, framework labels, and slugs are HTML-escaped before injection (reuse an existing `escapeHtml` helper; see Dev Notes).
9. Gallery/generation failure fails the build with an actionable stderr message (consistent with S27.2's `build:examples: …` errors).

## Dev Notes

### What exists — reuse, do not reinvent

- **Manifest loader (S27.1):** `scripts/lib/examples-manifest.mjs` — `loadExamplesManifest(repoRoot)` returns `{ hero, examples[] }` with each entry `{ slug, title, tagline, framework, commands?, landing? }`. Use `getHeroExample(manifest)` for the hero. **Do not** re-parse YAML anywhere else. Loader already validates catalog↔folder coverage.
- **Wiki generation (S27.2):** `scripts/build-examples.mjs` — `buildExamples({ heroOnly, all, siteOutputDir })` generates each slug via the compiled CLI (`dist/cli.js generate`), copies the staging `wiki/` tree into `dist/landing-site/examples/<slug>/`, then removes the staging dir and runs the URL guard. `--all` already builds every catalog slug. Emit the gallery hub **after** the slug loop in `buildExamples`, and only for the slugs actually built (so `--hero-only` won't advertise unbuilt demos). Guard `main()` behind the existing `isDirectRun` check — do not run generation on import (S27.2 review lesson).
- **URL safety guard:** `scripts/lib/assert-no-root-absolute-urls.mjs` → `assertNoRootAbsoluteUrlsInHtmlTree(dir)`. Call it over `dist/landing-site/examples` (or per-slug + hub) so the hub page is covered by AC 7.
- **Page shell pattern:** `scripts/build-blog.mjs` builds a static hub index from a shell (`renderPageShell`, `renderHeader`, `renderFooter`) using `../index.html` for the home link and `../assets/landing.css` for styling — the gallery lives at the same one-level-deep depth (`dist/landing-site/examples/index.html`), so copy those relative-path conventions exactly. `escapeHtml` is exported from `build-blog.mjs`; either import it or lift it into a tiny shared `scripts/lib/html.mjs` (preferred if you want to avoid coupling gallery → blog). Choose one and keep it consistent; do not hand-roll a second escaper.
- **Site copy build:** `scripts/build-landing-site.mjs` copies `site/` → `dist/landing-site/` and injects §04 from the manifest. It does **not** build examples — the deploy workflow runs `build:examples` separately, then `build:site`. The gallery `index.html` is produced by `build:examples`, so it lands under `dist/landing-site/examples/` before or after `build:site` copies `site/` (they write disjoint paths: `site/` has no `examples/` dir). Verify ordering in the workflow keeps both outputs.

### Frozen contracts / guardrails (project-context.md)

- ESM only; relative imports need `.js`/`.mjs` extensions. Scripts are `.mjs` with JSDoc types (see existing scripts).
- Manifest is the **single source of truth** for example metadata — no hardcoded titles, taglines, counts, or slug lists in HTML or copy (S27.1 review lesson: full-value comparison, not substrings).
- Never write outside the resolved output dir; generated wikis stay under `dist/` and are never committed (S27.2 AC 4). The staging `examples/<slug>/wiki/` dir is gitignored and removed after copy.
- Do not touch the frozen CLI wiki-output contract (`src/output/`). This story only assembles already-generated wiki trees into a hub.
